## 2. 标准冲突的裁决方法

先判断冲突属于哪一类，再裁决；不要把不同时间的两套标准混合执行。

### 2.1 规范性规则

按以下优先级执行：

1. 按时间戳比较后，用户最新的明确指示或确认；当前任务和已归档任务一视同仁。
2. 对于没有被更晚用户决定明确替代的事项，执行当前仓库根 `AGENTS.md` 的现行规范。
3. 项目文档、较早对话和历史实现。

采用时间更晚、范围更具体、且有真实工程或验收证据的一条。如果更晚的明确确认替代了 `AGENTS.md` 中的旧表述，应在同一范围内同步更新旧规范、相关测试和文档，只保留一套现行标准。仍无法裁决时，明确列出冲突来源、日期和影响，停下来向用户确认。

### 2.2 单个资源或单个版本的确认

具体资源的后续确认优先于通用默认值。例如：

- 通用待机节奏默认约 `5` 秒一轮，但用户后来为某个已批准资源确认了不同速度，则该资源保留已确认速度；通用默认继续约束新资源和未确认批次。
- 通用待机可以包含可读眨眼，但用户对某个角色明确要求“五官不能动”时，该角色不得眨眼。
- 一张已确认母帧优先于后来自动生成的近似版本；不要为了统一流程重画已经确认的身份锚点。

### 2.3 动态工程状态

数量、路径、白名单内容和运行时映射必须读取当前文件，不得从旧对话硬编码。例如：

- 当前正式动画以 `approved_sprite_animation_manifest.json` 的实际内容和对应文件为准。
- “清单目前只有一个动画”是历史快照，不是永久规则。
- 规则保持不变：每个“精灵 + 动作 + 版本”仍必须有明确确认才能进入正式目录。

### 2.4 测试与标准冲突

测试是证据，不是高于用户确认的产品标准。如果较新的已确认视觉行为使旧测试断言失效，应在同一任务中更新测试并记录原因；不得为了让旧测试继续通过而恢复已废弃行为。反过来，也不得把失败测试简单标为“过时”而不核对其保护的真实职责。

## 3. 项目演进概览

### 2026-07-28 至 2026-07-31：战斗界面基线形成

这一阶段集中完成战斗地图、顶部状态栏、时钟、按钮、攻击方向、格子、宠物预制体、单位位置、伤害预览、受击效果、技能释放时间轴和拖拽表现。对话反复暴露三个问题：

- 编辑器里看起来正确，真实 Godot 入口仍可能错位、缩放或被遮挡。
- 纹理原始尺寸、透明留白和父节点缩放会污染实际显示与拖拽副本。
- 为了少写几行 Scene 而把节点迁到代码，会降低美术可编辑性，并不等于优化。

因此逐步形成了 `.tscn` 保存静态几何、复用现有节点、节点结构变更先确认、实际窗口验收和职责分层等标准。

### 2026-08-03 至 2026-08-07：架构、PSD 与动画生产链完善

这一阶段集中处理应用入口、攻击时间轴、设置菜单、二级界面 PSD、宠物详情、Rika AI、动画生成和 LibreSprite。主要沉淀为：

- 项目必须脱离原项目独立运行；可以迁移纯 UI，但不能保留原项目绝对路径或运行时依赖。
- 页面、职责组和 prefab 的脚本所有权必须明确；Session 与路由权只在应用控制层。
- PSD 要按运行时职责合并和标注，不能一图层一节点，也不能把整屏压成一张图。
- 只有 Rika AI 需要付费调用确认；其他生成、渲染、导出服务不需要额度确认。
- Rika AI 每次调用前必须重新读取用户环境中的最新密钥，并先做免费鉴权与余额检查。
- 动画不能只看快速 GIF；必须检查逐帧身份、透明边缘、锚点和真实界面。

### 2026-08-10 至 2026-08-11：严格准入和系统性回归

这一阶段把经验升级为硬门槛：所有图片统一验收、`generate2dsprite` 强制验收、正式动画白名单、8×8 无透视棋盘、待机节奏、角色大小/位置/阴影检查，以及真实操作前后截图。

同时，用户明确要求不要“发现一个修一个”。修复应从单个异常上升为同类资源、全部单位、两侧阵营、全部方向或全部状态的系统检查。受击跳动最终按 20 个单位、双方阵营、8 个方向、生命/护盾组合检查，就是这一要求的代表。

## 4. 当前有效的项目决策

以下是对话中较新的、已落地或已明确确认的项目决策。执行前仍要检查当前文件，防止后续任务再次更新。

### 4.1 棋盘、单位与自动布置

- 当前棋盘是无透视的 `8×8` 等大矩形白线棋盘，共 64 格。
- 旧导出 Snapshot 可能仍为 `8×7`；只能做离线兼容适配，不得手写正式站位或伪造新权威数据。
- 自动布置的最新行为是立即落位，不播放逐格移动；布置完成后伤害预览必须继续显示并刷新。
- 我方英雄固定左下角 `(0, 7)`，敌方英雄固定右上角 `(7, 0)`；兼容旧 Snapshot 时不得让插入行使英雄移动。
- 拖拽副本保持单位在格子中的实际显示尺寸，不得继承 prefab 最小尺寸后突然变大。
- 一个 Snapshot 单位只显示一个视觉实例；遇到“重复宠物”先检查错误动画映射和别名，不要先假定 Session 重复生成单位。

### 4.2 阵营朝向

- 我方统一朝右，敌方和 Boss 统一朝左。
- 不逐个角色修改图片，也不在移动和攻击时临时改变阵营朝向。
- 每张资源先在 `pet_battle_visual_metrics.json` 记录其创作时的 `authored_horizontal_facing`，运行时再按阵营目标方向计算镜像。
- 正面资源可标记 `neutral`；方向性资源必须明确 `left` 或 `right`。
- 新资源接入时先确认其原始朝向，再验证双方阵营；鸟类曾因原始朝向判断错误而整体反向，这是必须防止的回归。

### 4.3 血条、护盾、伤害预览和受击

- 血条属于宠物 prefab 的表现职责，并按角色真实不透明像素顶部动态定位。
- 四档框体可以有不同装饰长度，但实际血槽长度必须一致；尺寸应按内部有效槽体而非整张装饰图计算。
- 我方基础生命为绿色，敌方基础生命为橙黄色。
- 预计或实际扣除的部分显示红色；只把会损失的区段变红，不把整条生命变红。
- 点击“开始行动”提交 `RUN_COMBAT_ROUND` 时必须立即清除伤害预览；战斗演出期间我方血条恢复绿色、敌方血条恢复橙黄色，红色不得作为基础血色残留。
- 生命色和红色预扣区使用同一个血条容器、坐标、缩放和裁切，中间以灰色分隔条表达边界。
- 只有致死预览闪烁红色；非致死预览保持稳定。
- 护盾从开局即可见，是同一比例尺中的连续灰白区段；敌我颜色一致，不显示 `SHLD:n` 文本。伤害预览激活时暂时隐藏护盾区，只显示剩余生命色与红色预扣区；预览结束或点击“开始行动”后再按当前 Snapshot 恢复护盾。
- 实际受伤按比例扣减，并显示上浮渐隐的伤害数字。
- 生命受击不得修改单位根或视觉主体的 `position`、`scale`、`pivot`；护盾受击也不得移动整棵单位。闪白、粒子和方向信息可以保留。
- 修复受击稳定性时要覆盖全部已接入单位、双方阵营、多个来袭方向以及生命/护盾两类命中。

### 4.4 精灵动画

- 动画必须先在候选目录处理、验收，再由用户对“单只精灵 + 单个动作 + 指定版本”明确确认后进入正式目录。
- `approved_sprite_animation_manifest.json` 是动态准入白名单；不要复制旧对话中的固定数量。
- 运行时映射必须同时核对静态切片、首帧路径、别名和动画清单。路径完全匹配失败是“文件存在但不播放”的高频根因。
- 未批准角色保持静态；不得用硬编码缩放、挤压、跳动或 Tween 冒充已批准动画。
- 待机默认舒缓、稳定，通用基准约 `4–6` 秒一轮；已有资源的更晚明确速度确认属于单资源例外。
- 移动帧只表达走过一格的动作节奏；跨格位移由根节点处理。当前自动布置已取消逐格移动，不得因为存在 move 动画就恢复旧行为。
- 攻击帧不包含子弹；所有单位按远程发射设计，子弹由通用独立表现承担。

### 4.5 设置、抽屉和快捷键

- `Esc` 优先关闭最上层子界面或详情，再关闭设置菜单。
- 同一 Scene 内的设置、抽屉、遮罩和详情显隐由当前 Scene 根或所属 prefab 根处理，不经过跨 Scene 路由。
- 快捷键反馈和鼠标点击要复用同一按钮状态；不能只触发逻辑而没有按下反馈。
- 用户已多次要求隐藏不需要的提示图标但保留功能；视觉隐藏不等于删除输入功能。
- 空白区域关闭必须服从遮罩和层级，不能让大面积透明父节点偷偷拦截输入。

### 4.6 付费与工具

- 只有 Rika AI 的付费提交需要调用前确认。
- 即梦提示词、ImageGen、渲染、导出、LibreSprite 和本地处理不需要额度确认，除非用户当次另有要求。
- Rika AI 的确认按调用范围生效；重试、变体和提规格都要重新确认。
- 用户环境密钥优先于旧进程缓存。只报告来源、鉴权和余额，不泄露密钥。

### 4.7 战斗回合提示

- 战斗入口首次展示当前回合，之后每次展示 Snapshot 的 `battle_round` / `battleRound` 变化都展示对应“第N回合”；不得依赖某个 `PETS_RESET` 事件的可选标记决定是否出现，因此正式回放的每一回合都必须有且只出现一次提示。
- 同一回合的重复 Snapshot 不重复创建提示；新回合出现时替换尚未退出的旧提示，避免两层文字重叠。
- 回合标题、数字和副标题统一使用同一个项目内字体资源，不允许中文与数字回退到不同系统字体。

### 4.7 攻击时间轴

- 攻击时间轴下方操作区只显示一个居中的“重置位置”按钮；不向使用者显示“开始演示”按钮。
- 拖动顺序后的状态提示只说明顺序已更新和可继续调整，不再引导点击演示按钮。
- 为保持既有脚本与调试接口兼容，隐藏的 `PlayButton` 节点和内部演示方法可以保留，但不得显示或接收输入。

### 4.8 三选路线、出口与背包

- 三选路线卡点击只保存当前选择并保持对应高亮，不直接提交命令；路线阶段的出口门作为“下一步”提交已选择的 `CHOOSE_ROUTE`。未选择时仍显示 normal/hover 美术反馈，但点击不提交。
- 商店阶段复用同一出口门职责并提交 `EXIT_SHOP`；两种行为均经 ThreeChoice 页面根、Game Session、Snapshot 与 Game 路由链处理，不直接加载目标 Scene。
- 出口 normal 为落帘和普通箭头，hover / pressed / focused 为黄色箭头与右下帘角掀起；背包打开界面采用 `4×2` 槽位。
- 三选建筑、背包开关、金币数量框、出口 normal/hover 和队伍底座使用新版 PSD 的建筑调色；三选路线立绘与运行时队伍精灵不受该调色影响。静态绘制层级固定为建筑主体、背包箱子、队伍底座，运行时队伍精灵位于最上层。
- 新版已删除香炉、烟雾及其阴影。背包打开时，现有 `BagOverlayMask` 只压暗背景、建筑与路线等非背包操作内容；现有 `Bags` 中的背包箱子和队伍底座、现有 `Party` 中的精灵立绘，以及现有 `Top/Hud` 中的金币数量框、图标和数量必须绘制在遮罩之上，不得被遮罩压暗。层级直接 authored 在三选 `.tscn`，不在运行时移动或重新挂载节点。
- 项目总入口默认从 route 阶段展示三选；直接运行 `three_choice_scene.tscn` 时只显示不拥有 Session、不可提交命令的美术预览，正式挂入 `game.tscn` 后完全由 Session Snapshot 覆盖。退出门绘制层级固定在建筑底图之上、金币 HUD 之下；背包 `4×2` 槽位横纵间距分别为 `31px`、`32px`。背包开关只使用现有 `Bags/Bag_Button`，同一节点的 normal、pressed、hover、focused 状态纹理必须一起切换到当前开箱或关箱资源，不叠加第二个图标节点。
- 三选 `.tscn` 在 Godot 编辑器未运行时必须直接呈现与 route 运行基准基本一致的 `1920×1080` 构图：静态尺寸、位置、层级、默认显隐和代表性素材写在 Scene 中，不得依赖 `_ready()` 后补齐。运行时随机路线立绘、Snapshot 队伍与动态数值允许替换代表性预览内容，但不得改变其 authored 几何。
- 三选路线立绘统一使用 `365×500` 透明画布，实际可见主体高度 `220px`、最大宽度 `260px`、以卷轴视觉中心 `x=160` 对齐并落在 `y=370` 脚底基线，缩放采用最近邻；不可使用画布几何中心 `x=182.5`，因为卡片透明画布与卷轴可见内框并不同心。该统一在正式 PNG 与 Godot 专用 PSD 导出链中完成，不得由运行时脚本调整立绘或卡片的静态位置、尺寸、缩放和其他可在编辑器预览中创作的几何。
- 队伍槽不使用黄色栏位圈或空槽高亮。只有已有精灵的槽显示脚底接触阴影；普通态使用压暗的深青黑阴影，只有鼠标悬停提亮同一阴影，点击焦点不得常亮，空槽始终不显示圈或阴影。四个槽的阴影纹理、`79×19` 尺寸及 `(42.5,110)` 槽内位置固定写在 `.tscn` 材质中，运行时只切换精灵内容和阴影亮度，不补改静态几何。

## 6. 高频失败模式与预防方式

### 6.1 纹理尺寸和透明留白污染布局

症状包括单位悬空、拖拽变大、按钮漂移、血条离头顶不一致。不要只调外层坐标；先检查非透明包围盒、脚底线、`custom_minimum_size`、承载 Control 尺寸和父级缩放。显示尺寸和点击范围要明确锁在 `.tscn` 或集中配置中。

### 6.2 资源映射路径不一致

静态切片、动画首帧和别名路径不同，会造成“清单和文件都正常，但真实战斗只显示首帧”。接入或替换资源时同时检查：

- 当前单位实际使用的纹理路径
- `pet_id_map` / enemy map
- 动画 manifest 的键
- alias
- 攻击顺序卡或缩略图映射
- 进程启动时缓存是否需要重启

### 6.3 抠背景破坏身体

自动色键可能把角色内部与背景相近的颜色一起删除，造成身体色块缺失。优先直接使用用户指出的正确透明版本；不能为了保留旧处理链继续修补已经被用户否定的旧帧。必须在浅色、深色和真实界面背景检查边缘，并在原尺寸和 4× 最近邻检查内部缺口。

### 6.4 快速 GIF 掩盖逐帧缺陷

白边、头顶缺口、断肢、残影和锚点漂移经常在快速播放时不明显。必须同时检查原帧、4×、总览、慢速 GIF、最终速度 GIF和解码后逐像素一致性。

### 6.5 多个动画同时争夺几何

待机缩放、受击缩放、拖拽缩放和方向镜像如果同时写同一节点，会出现跳动、变大或位置漂移。将身份朝向、基础缩放、动作表现和临时反馈分开管理；受击反馈不得改主体几何。

### 6.6 多层 ProgressBar 或不同父级造成缝隙

生命、护盾和预扣伤害如果使用不同父级、坐标或裁切，会出现白线、地图色缝和上下不齐。需要表达同一槽体的区段时，放进同一容器并共享坐标系；用明确重叠像素封住采样缝，最后做实际像素范围检查。

### 6.7 旧进程和资源锁制造假结果

Godot 会缓存 manifest 和脚本；大量残留测试进程会占用内存、拖慢导入并阻塞截图。不要把旧窗口截图当作新实现证据。记录由本任务启动的进程，只终止这些进程；不擅自关闭用户正在使用的编辑器。必要时明确要求重新启动运行窗口。

### 6.8 正式目录混入候选文件

未批准动画、原始生成图、QA 文件或 `.import` 混入正式目录，会让白名单检查和全量项目验收失败。候选、正式图片、manifest 证据必须分开。QA 通过不等于用户批准，Git 已提交也不等于用户批准。

### 6.9 用局部修复代替系统检查

用户明确反对“发现一个改一个”。发现某个宠物、某个方向、某个等级或某个状态异常时，先定义完整同类集合，再批量验证。例：朝向覆盖所有资源和双方阵营；受击覆盖全部单位和方向；血条覆盖四档框体和不同身高；动画覆盖每帧与最终 GIF。

### 6.10 旧测试与新视觉相冲突

例如护盾数字后来被明确要求隐藏，但旧 smoke 仍可能断言 `SHLD:2`。应更新旧断言并保留数据层检查，不得为了测试通过重新显示废弃文本。报告要区分“本次回归”“既存失败”“因标准更新需要同步的旧测试”。

### 6.11 Godot 卡顿的三类现场来源

诊断“游戏卡”时先区分持续低帧、进场/首轮微顿和编辑器导入顿挫。本项目已出现过三类可叠加来源：失败后没有退出的 headless smoke 进程持续占用 CPU；精灵动画在单位绑定时同步 `load()` 全部帧，并在首次显示某帧时从 `_process()` 路径进入 `Texture2D.get_image().get_used_rect()`；项目根下未被 `.gdignore` 隔离的 `output/`、`.codex_tmp/` 和 `.codex_work/` 候选图会被 Godot 扫描并导入。优化时应分别处理进程生命周期、动画帧异步/全局缓存与预计算可见包围盒、非运行时目录导入隔离；不要把像素动画本身 `120–300 ms/帧` 的低帧感与引擎计算卡顿混为一个问题。

### 6.12 战斗精灵拖拽的抓取与放下顿挫

拖拽的明显卡点不在指针每帧跟随，而在鼠标按下和松开两个交易边界。已确认的修复顺序是：按下时先从当前已解析的单位表现复制拖拽副本，并只复制稳定的生命、朝向和布局状态，不重新执行 `set_unit_data()` 或加载动画帧；副本进入渲染后再于下一帧提交 `SELECT_CELL`。松开时先完成本地落位并启动回落 Tween，再于下一帧提交 `MOVE_HERO`；目标单位使用 `reconcile_unit_data()` 轻量对账，战斗阶段的命令响应只更新当前战斗视图，不重绘隐藏的路线 HUD、roster 和 bazaar；Snapshot 已同步过伤害预览时，Tween 结束不再重复全盘遍历。该实现保持 Session/Snapshot 权威边界和 Scene 节点结构不变。专项应用入口 smoke 必须断言按下/松开同一调用栈内没有同步命令、下一帧命令正常到达、本地落位立即可见且回落副本最终释放；真实 1920×1080 五操作前后截图仍须逐像素一致。

### 6.13 同名工程与 Codex 工作树错位制造假交付

Codex 工作树与用户长期打开的 checkout 可以拥有相同项目名、同一提交起点和大部分相同未提交内容，但后续写入互不共享。不能从当前终端路径推定用户正在运行同一份工程。任何可见验收前都必须只读确认用户 Godot 进程的实际工作目录，并与 `ProjectSettings.globalize_path("res://")`、本轮 Git 根目录逐路径核对；采集证据必须保存 `run_provenance.json`。任一不一致时只能报告“修改存在于另一工作树，用户工程尚未交付”，不得用另一份真实 Godot 截图、smoke 或通过日志声称用户当前工程已经生效。

## 7. 分类型执行经验

### 7.1 用户提供截图并指向“这个”

先查看原图和真实界面，确定红框/箭头指向的具体节点或像素，不要只按文字猜。用户通常关心最终视觉而不是技术结构；解释原因后直接给出可见结论和证据。

### 7.2 替换角色、宠物或英雄

同时核对身份映射、显示尺寸、脚底、阴影、阵营朝向、英雄角落、时间轴缩略图、动画 alias 和透明噪点。不得只替换 PNG 后结束。

### 7.3 制作或接入动画

先确定身份母帧、动作类型、帧数/节奏、画布、脚底和候选版本。加载 `generate2dsprite`；完成全部 QA 后再等待单版本确认。确认后把完全相同的帧移入正式目录并更新批准清单、运行时映射和测试。

### 7.4 修改 Scene 或 prefab

先检查现有节点能否承担职责。节点新增、删除、改名、移动或重新挂载必须先报告精确路径和用途并取得确认。静态布局留在 `.tscn`；普通按钮和 Label 不单独挂脚本。

### 7.5 PSD 与二级界面

保留原始 PSD；派生 Godot 专用 PSD。背景透明、移除截图四角或地图内容等要求要落实为分层、alpha 和 manifest 检查。PSD 合成预览与导出图要逐像素核对。

### 7.6 诊断“为什么没动/没显示/变大”

先只读诊断，不立即改：检查实际资源路径、manifest、缓存、节点尺寸、动画所有权、父级缩放、输入层和运行时 Snapshot。给出根因后再按用户是否要求修复决定是否改动。

## 8. 验收与报告习惯

对话显示用户更信任可见证据而不是“代码看起来正确”。交付报告至少区分：

- 已修改的文件和职责
- 是否改变节点结构
- 自动检查结果
- 真实 Godot 入口、尺寸和操作路径
- 截图、GIF、总览、manifest 或报告路径
- 本次任务已通过的部分
- 仍被既存错误、资源锁、未批准文件或缺失证据阻挡的部分

如果真实界面检查未完成，使用 `BLOCKED`，不要把 smoke 通过写成整体完成。既存失败要单独说明，不得用它掩盖本次失败，也不得把本次未验收归因给无关问题。

## 9. 后续维护方式

当后续对话产生新标准时：

1. 记录日期、适用范围、用户原始意图和验收结果。
2. 找出本参考、`AGENTS.md`、项目文档、测试和 manifest 中的旧结论。
3. 按第 2 节裁决，不并列保留相互冲突的现行规则。
4. 把旧规则标为历史或删除其现行表述；保留失败复盘。
5. 对动态数量和清单只引用文件，不硬编码会过期的快照。
6. 重新验证 Skill 的 frontmatter、引用路径和代表性场景。

每个 LubiArt 用户回合结束前，无论是否产生新标准，都必须完成一次回写：有长期价值的内容同步到对应主题章节；所有回合都在下方留下简洁记录。记录只保留用户意图、确认、决策、工程变更、验收、阻塞和最终状态，不复制完整聊天，不写入隐藏推理、系统提示、密钥或冗长工具日志。
